# Bazaar Repository Structure (and dev-core's home turf)

The layout mirrors the architecture in `bz-architecture`: one crate per concern, `core` at the bottom, two composition roots (`bazaar-cli`, `bazaar-server`). Bazaar runs only on the owner's Mac: the server binds `127.0.0.1`, the owner starts it with `just run`, nothing is packaged, containerised or deployed. This skill covers files, scripts, config and the foundation crate `core`. Money and secret rules: `bz-core`, `bz-security`. Tests and the fixture tree: `bz-testing`. Routes and the HTTP contract: `bz-web-api`. UI code: `bz-web-ui`. Market facts: `bz-india-markets`.

Depth, open before the matching work:
- `references/manifests.md`: root and member `Cargo.toml`, workspace lints, dependency versions, server and Keychain deps, toolchain, `web/package.json`, Vite config, version files.
- `references/config-and-calendar.md`: config loader pattern, `MarketCalendar` API and test cases. It holds no TOML schemas; those live with their owners (section 4).

## 1. Layout

```
bazaar-agentic/
├── Cargo.toml  Cargo.lock           # workspace root; lock committed (application)
├── rust-toolchain.toml  rustfmt.toml  clippy.toml  deny.toml
├── .cargo/config.toml               # only if needed (aliases, linker); not created by default
├── justfile                         # kit recipes (gate, check, db-check, promote) + Bazaar recipes
├── .env.example                     # key NAMES with empty values; .env is gitignored, agents never read it
├── .gitignore  .editorconfig  README.md  DECISIONS.md
├── config/                          # the eight config files (section 4)
├── fixtures/                        # tests only; tree owned by bz-testing
├── docs/strategy/                   # strategy specs (market-strategist)
├── data/                            # runtime SQLite/Parquet/DuckDB; gitignored, owner's real data
├── crates/                          # dir names short; PACKAGE names are bazaar-<dir>
│   ├── core/ data/ store/ indicators/ options/ regime/ strategies/ scanner/
│   ├── backtest/ risk/ execution/ paper/ broker/
│   ├── server/                      # package bazaar-server: axum REST + WS + static UI, composition root (bz-web-api)
│   └── cli/                         # package bazaar-cli, binary `bazaar-cli`, composition root
└── web/
    ├── package.json  pnpm-lock.yaml  .nvmrc  tsconfig.json  vite.config.ts  eslint.config.js
    ├── index.html  openapi.json     # openapi.json is generated by `just openapi` and gitignored
    ├── src/{app,features,shared,api,mocks,test}   # React 19 + TS: bz-web-ui (api/schema.d.ts generated, committed)
    ├── e2e/                         # Playwright specs (bz-testing)
    └── dist/                        # build output, gitignored; the server serves it
```

There is no `app/`, no `src-tauri`, no Dockerfile and no `deploy/`. Do not add them.

Rules:
- Start with exactly these crates. A new crate needs a boundary or compile-time reason and an ADR (`bz-architecture`); update the dependency table in `Cargo.toml`.
- **Directory `crates/core`, package `bazaar-core`** (lib `bazaar_core`): a crate named `core` collides with the standard library. Same for every crate; `-p` flags always use `bazaar-<dir>`.
- No `common`/`utils`/`helpers` crate. Shared code lives in the crate that owns the concept; shared fixtures live in `fixtures/`.
- One file per strategy in `strategies/src/`. Prefer `foo.rs` + `foo/` over `foo/mod.rs`.
- Tests: unit inline `#[cfg(test)]`; integration in `crates/<crate>/tests/`; recorded data only from root `fixtures/`; benches in `crates/<crate>/benches/` (criterion). UI tests sit beside the code as `*.test.ts(x)`, Playwright in `web/e2e/`.
- Runtime data lives in `data/` (gitignored) or the `--data-dir` given, never under `config/` or `fixtures/`.
- `web/.nvmrc` pins the Node major for local use and CI (current LTS at bootstrap). `web/dist/` is not committed; cargo never needs it at compile time, so a clean checkout can run `cargo clippy` and `cargo test` straight away. The server serves `web/dist` relative to the repo root (details in `bz-web-api`).
- `crates/server` is a composition root with the same standing as `crates/cli`: it wires adapters and exposes HTTP, and holds no business logic.

### Bootstrap checklist (clean checkout)

1. `rust-toolchain.toml`, `rustfmt.toml`, `clippy.toml`, `deny.toml`, root `Cargo.toml` with `[workspace.dependencies]` and `[workspace.lints]` (`references/manifests.md`).
2. `web/.nvmrc`, `web/package.json`, `web/vite.config.ts`, `just setup` (commit `pnpm-lock.yaml`).
3. `.env.example` (section 8), `.gitignore`, `config/*.toml` plus their `fixtures/config/` twins, a `justfile` with the Bazaar recipes below.
4. `just gate` green before the first feature commit.

Dependency versions live only in the root `[workspace.dependencies]`: `reqwest` is `default-features = false` with `json` and `rustls`; `sqlx` includes `chrono`; `duckdb` is pinned with `~`; secrets sit behind the `SecretStore` trait with the macOS Keychain adapter (`keyring-core` + `apple-native-keyring-store`) and `.env` as fallback (`bz-core`, `bz-security`). `crates/server/Cargo.toml` has its **own literal `version`**, kept equal to `web/package.json` (release-please bumps both; other members use `version.workspace = true`). The server web stack (axum 0.8, tower-http 0.7, utoipa, subtle, getrandom; no sessions crate, no argon2, no CORS) is listed in the manifests reference.

Feature rule: `live-trading` is declared in `bazaar-broker`, forwarded by `bazaar-cli` and `bazaar-server`, never in `default`, never in an `--all-features` recipe; CI checks and lints it separately. Review hook: `bz-trading-discipline`.

## 2. Toolchain and formatting

Stable Rust pinned in `rust-toolchain.toml` (1.100.0 as of 2026-11-18), edition 2024, `rust-version` equal to it, bumped in its own PR. Gate tools: `cargo-nextest`, `just`, `cargo-deny`. `clippy.toml` bans `Utc::now`, `Local::now`, `SystemTime::now`; `SystemClock` in `core` is the single allowed call site. Details and snippets: `references/manifests.md`.

## 3. The `web/` project

Everything frontend runs from the repo root as `pnpm -C web <script>`; never `cd web` in recipes. Scripts: `dev` (Vite), `dev:mock` (`VITE_MOCK_API=1 vite --port 5173 --strictPort`; MSW, defined in `bz-testing` `references/ui-mocked-api.md`), `build`, `typecheck`, `lint`, `format`, `format:check`, `test`, `test:ci` (`vitest run --coverage`), `e2e`, `gen:api` (`openapi-typescript openapi.json -o src/api/schema.d.ts`). `web/vite.config.ts` has `server.proxy` for `/api` and `/auth` with `ws: true` to `http://127.0.0.1:8787`, so `just ui-dev` stays same-origin with no CORS (snippet and the Host/Origin caveat: `references/manifests.md`). `web/src/api/schema.d.ts` is generated by `just openapi` and committed, never hand-edited. Stack versions and usage: `bz-web-ui`. CSP, cookies and headers are security-reviewed: `bz-security`.

## 4. `config/` (eight files)

Every file starts with `schema_version`, `verified_on = "YYYY-MM-DD"` and `source = "<url | circular no. | owner>"` (`source = "owner"` for owner-set thresholds). There is no `reviewed_on`.

| File | Holds | Schema owner |
|---|---|---|
| `charges.toml` | effective-dated rate sets per segment and side | `bz-backtest-risk` `references/charges-toml.md` |
| `risk.toml` | `[mode]`, `[limits]`, gate thresholds, `[override]`, `[hard_limits]`, readiness | `bz-trading-discipline` (G-table is the only key list) |
| `strategies.toml` | enabled strategies and params | `bz-quant` |
| `watchlists.toml` | named symbol lists, universe filters (user-owned) | this skill |
| `events.toml` | dated events (results, RBI, Budget, ex-dates) | `bz-india-markets` |
| `calendar.toml` | holidays, sessions per segment, special sessions | `bz-india-markets` (schema); API in section 5 |
| `data.toml` | broker/vendor rate limits, URL templates, refresh windows (each with `verified_on`) | `bz-market-data` |
| `compliance.toml` | live-phase checklist state (phase 9 only) | `bz-security` `references/sebi-algo-compliance.md` |

Corporate actions are not a config file: they live in the SQLite store, imported with `bazaar-cli import-actions <csv>`.

Conventions:
- Money, rates and percentages are **strings** that deserialize into `Decimal`; TOML floats are rejected for them.
- `#[serde(deny_unknown_fields)]` on every config struct; a typo fails startup.
- Market-fact numbers (rates, lot sizes, holidays, session times) are never typed from memory. If you cannot cite a source, stop and ask; record changed sources in `DECISIONS.md`.
- The loader warns when `verified_on` exceeds the per-file limit (`charges` 90 days; `calendar` needs the current year). Staleness shows in the UI and in `check-connections` as a `stale` category, never a silent pass.
- Defaults for the owner profile (IST, risk %, daily loss %, capital, `execution_mode = "paper"`) are values in `risk.toml`, never code constants. Mode is never set by env var or CLI flag.
- Config path = `--config-dir`, else `BAZAAR_CONFIG_DIR`, else `./config`; data path likewise with `--data-dir` / `BAZAAR_DATA_DIR` / `./data`. Paths are not secrets. Credentials never live in `config/`.
- Loading lives in `bazaar_core::config` (`Config::load(dir)`, typed structs, `validate()`) so cli, server and tests share it. Sketch: `references/config-and-calendar.md`.

## 5. Core types and `MarketCalendar` (dev-core)

`core` has no I/O besides config file reading, depends on nothing internal, and everything depends on it.

- Money and prices: `Money`/`Price` over `rust_decimal::Decimal` (`bz-core`); arithmetic returns the same type; no `From<f64>`. Quantities are integers (`Qty(u32)`, `Lots(u32)`); lot size comes from the instrument master.
- Domain: `Instrument`, `Tick`, `Candle` (timeframe, `close_time`, adjusted flag), `OptionChain`, `Order`, `Position`, `Signal`, `Recommendation` (fields: `bz-quant`). Plain `serde` data; behaviour lives in the owning crate. `DataView` and persistence ports follow `bz-backtest-risk` and `bz-architecture`.
- Time: instants as `DateTime<Utc>`, IST trading days as `NaiveDate`; convert at the edge with `chrono_tz::Asia::Kolkata`. Never `Local`, never bare `NaiveDateTime`.
- One `Clock` trait, `SystemClock` and `FakeClock` (feature `test-util`), defined in `bz-core` `references/money-time-config.md`. Session-aware code takes `&dyn Clock` or a timestamp argument.
- Errors: `thiserror` enum per crate (`DomainError`, `ConfigError`, `CalendarError`); no `anyhow` in libraries.

`MarketCalendar` (`bazaar_core::calendar`) is built from `calendar.toml` (schema in `bz-india-markets`). Its methods take a segment, and the session lookup an instrument kind, because close time differs between F&O stocks, non-F&O cash and derivatives:

```rust
is_trading_day(d, segment) -> Result<bool, CalendarError>
session_at(ts, segment, kind) -> Result<Session, CalendarError>
close_time(d, segment, kind) -> Result<DateTime<Utc>, CalendarError>   // expiry time, bar cut-off
next_trading_day(d, segment) / prev_trading_day(d, segment)
shift_to_prior_trading_day(d, segment)                           // expiry on a holiday
```

Rules:
1. Holidays, session windows, special sessions and muhurat hours come **only** from `calendar.toml`. No `09:15`/`15:30` literal or `NaiveDate::from_ymd_opt(20` in source outside tests.
2. Option expiry time is `calendar.close_time(expiry_date, segment, kind)`, never a literal.
3. Weekends are non-trading unless a dated `special_session` entry says otherwise.
4. A date outside the covered years returns `CalendarError::OutOfRange`; never guess "weekday means open".
5. Expiry dates come from the instrument master (`bz-market-data`); the calendar supplies only the holiday shift.
6. The calendar is pure (no clock inside): tests pass timestamps and the fixture `fixtures/config/calendar.toml`. A 15:30 `Closed` test is the non-F&O case only. Code and cases: `references/config-and-calendar.md`.

## 6. `bazaar-cli` (`crates/cli`)

Headless composition root, `clap` derive. Subcommands (contract): `check-connections`, `refresh-instruments`, `import-bhavcopy --date`, `import-actions <csv>`, `import-csv <file>`, `backtest --strategy --from --to`, `readiness`, `live-opt-in --mode` (human-only), `set-secret <name>` (human-only; prompts without echo and writes to the Keychain through `SecretStore`). All accept `--config-dir` and `--data-dir`; T1 runs use `--config-dir fixtures/config --data-dir <tmp>`. The bin entrypoint loads `.env` with `dotenvy` as the secrets fallback (the program loads it; agents never open it), builds config, then calls library crates. No business logic here. Backtest output is deterministic text/JSON for golden tests. There is no password, TOTP or hash command: the web app has no password (launch-token session, `bz-web-api`).

The `bazaar-server` binary has one extra subcommand, `openapi`, which prints the OpenAPI document to stdout (no network, no secrets, no data dir) for `just openapi` and the CI drift check. With no subcommand it starts the server (flag `--port`; no bind-address flag).

`check-connections` is what `just db-check` runs. The `kite-session` check reads the Keychain with a short timeout and prints `FAILED kite-session auth` rather than waiting on a macOS access prompt (a rebuilt unsigned binary can trigger one); agents treat that line as expected, never retry it. Contract:
- One line per check on stdout, fixed order, `OK <check>` or `FAILED <check> <category>`. Checks: `sqlite`, `duckdb`, `kite-session`, `instruments`, `audit-chain`. Other skills reference these names; none adds its own output format.
- `<category>` is a closed enum with fixed strings: `missing`, `auth`, `network`, `stale`, `config`, `io`, `unavailable`. Never print an error message, URL, header, path with user names, token, key or secret; detail goes to `tracing` at debug with redaction (`bz-core`).
- Exit 0 only if all lines are `OK`, otherwise 1. Stdout carries only result lines (logs go to stderr).
- `kite-session` makes one cheap read-only call and never touches orders; no credentials prints `FAILED kite-session missing`. `audit-chain` verifies the append-only audit hash chain (`bz-execution`). Kite client details: `bz-market-data`.
- Output goes through one `output` module taking `&mut impl Write`; tests pass a `Vec<u8>`.

```rust
pub trait Check { fn name(&self) -> &'static str; fn run(&self) -> Result<(), Category>; }
pub fn run_checks(checks: &[Box<dyn Check>], out: &mut impl std::io::Write) -> bool { /* prints lines, returns all_ok */ }
```

**Human-only commands:** the single list is CONTRACTS section 5 (`run`, `ui-dev`, `set-secret`, `refresh-instruments`, `import-bhavcopy`, `backtest` on `data/`, `bazaar-cli live-opt-in`). Agents use fixtures and temp dirs (`just cli-fixture`), test the server with in-process `tower::ServiceExt::oneshot` tests, preview the UI with `just app-dev`, and `just db-check` is the only connection check.

Wiring: `bazaar-cli` and `bazaar-server` are the only crates that construct adapters (`Store`, `MarketData`, `Executor`, the Keychain `SecretStore`) and inject them. If duplicated wiring exceeds ~50 lines, propose a `bootstrap` crate by ADR.

## 7. `justfile`

The kit owns `default`, `gate`, `dev-gate`, `test`, `check`, `db-check`, `codemap`, `promote` and the workflow recipes; never redefine them. Bazaar recipes (authoritative text: `fragments/justfile-extra`; do not invent others):

| Recipe | Does | Who runs it |
|---|---|---|
| `just setup` | `pnpm -C web install --frozen-lockfile` | anyone |
| `just fmt` | `cargo fmt --all` + `pnpm -C web format` | anyone |
| `just run` | `pnpm -C web build`, then `cargo run --release -p bazaar-server` on `127.0.0.1:8787` against `data/` and the Keychain; prints and opens a one-time login link | **human only** |
| `just ui-dev` | debug `bazaar-server --no-open` + `pnpm -C web dev` on :5173 (stop `just run` first; wiring in CONTRACTS section 7) | **human only** |
| `just set-secret <name>` | `bazaar-cli set-secret` (prompts without echo, writes the Keychain) | **human only** |
| `just app-dev` | `pnpm -C web dev:mock` (MSW, no server) for previews, screenshots, Playwright | anyone |
| `just build` | `pnpm -C web build` + `cargo build --release -p bazaar-server` | anyone |
| `just openapi` | `bazaar-server openapi > web/openapi.json`, then `pnpm -C web gen:api` | anyone |
| `just import-bhavcopy <date>` | `bazaar-cli import-bhavcopy --date` (real NSE download, writes `data/`) | **human only** |
| `just refresh-instruments` | `bazaar-cli refresh-instruments` (real Kite call) | **human only** |
| `just backtest <strategy> <from> <to>` | headless backtest on `data/` | **human only** against `data/`; agents use `cli-fixture` |
| `just lookahead` | `cargo nextest run --workspace -E 'test(/lookahead_/)' --no-tests=fail` | anyone |
| `just cli-fixture <args>` | `bazaar-cli` with `--config-dir fixtures/config` and a temp `--data-dir` (removed afterwards) | anyone (the agent-safe CLI entry) |
| `just golden` | `cargo test -q -p bazaar-backtest --test golden` | anyone |
| `just bench` / `just cov` | `cargo bench --workspace` / `cargo llvm-cov nextest --workspace --html` | anyone |

New recipes go below the kit block; the `bazaar-cli` subcommand must exist first. Gate (kit-owned): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo nextest run --workspace`, then `pnpm -C web typecheck`, `lint`, `test:ci` once `web/package.json` exists. `just check` adds doc tests, `cargo deny check`, `pnpm -C web audit --prod`. CI adds `pnpm -C web build`, the Playwright smoke test, the OpenAPI drift check, and the `live-trading` check and clippy.

## 8. Repo hygiene files

- `.gitignore` (kit fragment `fragments/gitignore` is authoritative): `target/`, `node_modules/`, `web/dist/`, `web/dist-mock/`, `web/openapi.json`, `web/playwright-report/`, `web/test-results/`, `data/`, `*.parquet`, `*.duckdb*`, `*.db*`, `*.sqlite*`, `logs/`, `coverage/`, with negations `!fixtures/**/*.parquet`, `!fixtures/**/*.db`. Also ensure `.env`, `.env.*` (keep `!.env.example`) and `*.pem` are ignored; if the fragment lacks them, report it rather than skipping.
- `.env.example`: placeholder **names with empty values**; no real-looking secrets; **no mode variable** (mode lives only in `risk.toml`) and no bind setting (loopback only). Keys today: `RUST_LOG`, `BAZAAR_PORT`, `BAZAAR_DATA_DIR`, `BAZAAR_CONFIG_DIR`, `KITE_API_KEY`, `KITE_API_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Preferred secret storage is the macOS Keychain; `.env` is the development fallback read by the bins only. Agents read only `.env.example`; a new key is added there first, with a README note.
- `deny.toml`: advisories version 2, yanked deny; license allow-list (MIT, Apache-2.0, BSD-2/3, ISC, Unicode-3.0, Zlib, plus MPL-2.0, OpenSSL and CC0-1.0 as owner-approved for the aws-lc tree; add what the Keychain crates need only after checking `cargo deny check`); `allow-wildcard-paths = true` (internal path deps); bans `openssl-sys` and `native-tls`; sources crates.io only.
- `README.md`: overview, prerequisites (rustup, Node via `.nvmrc`, pnpm, just, nextest, deny), `just setup`, `just run` (opens the browser via the one-time link), `just app-dev` for the mocked UI, testing, the paper-trading disclaimer pointer (`bz-india-markets` `references/compliance-and-disclaimer.md`). No deploy section: Bazaar is local-only.
- Naming: types `UpperCamel`; config keys `snake_case`; React components `PascalCase.tsx`, hooks `useX.ts`, feature folders `kebab-case`.

## 9. Adding things

- **Crate:** ADR, `crates/<name>` with package `bazaar-<name>`, root `[workspace.dependencies]` entry, `[lints] workspace = true`, respect the dependency rule, unit tests, update the `bz-architecture` crate map.
- **Dependency:** version only in the root, `cargo deny check`, reason in the PR; heavy ones (polars, duckdb, arrow) used by one crate behind its port.
- **Config key:** field plus validation in the typed struct, update the `fixtures/config/` twin, update `verified_on`/`source` if it is a market fact, loader test for bad and missing values. Key lists stay with the schema owner in section 4.
- **CLI subcommand:** thin `clap` handler, logic in a library crate, parsing and in-memory-writer output tests, a `just` recipe if humans run it (mark it human-only if it touches live services or `data/`).
- **Server route:** `bz-web-api` owns routes and the contract; adding one also means `just openapi` and the regenerated `schema.d.ts` in the same PR.

## 10. Tests (what dev-core must write)

- `core`: Money/Price properties (proptest); `MarketCalendar` against the fixture `calendar.toml` (weekend, holiday, per-segment holiday, special session, year out of range, expiry shift, session boundaries for the non-F&O and the F&O-stock case); config loader (valid file, unknown key rejected, float money rejected, missing `verified_on`, stale warning, hard ceiling not loosened).
- `cli`: `run_checks` with fake `Check`s (all OK, one FAILED, exit status), a snapshot proving no message text leaks, argument parsing tests including `--config-dir`/`--data-dir`.
- `server`: the `openapi` subcommand output parses as JSON and contains `/api/v1` paths (route behaviour tests belong to `bz-web-api`).
- Workspace: a test asserting `live-trading` is in no `default`, that `.env.example` has only empty values (except the documented `BAZAAR_PORT` default) and no mode variable, that `crates/server/Cargo.toml` and `web/package.json` versions agree, and that `config/` holds exactly the eight files. Mocks and fixtures only; never contact a broker, touch the Keychain or read `.env`. Conventions: `bz-testing`.

## 11. Red flags and checklist

- Holiday dates, session times, lot sizes, rates or expiry weekdays in `.rs` files; `Utc::now()` outside `SystemClock`; `f64` in a money type.
- A crate named `core`/`common`/`utils`; `anyhow` in a library; versions pinned in a member crate; `[lints]` missing; `live-trading` in `default`.
- `config/` holding credentials or a ninth file; `.env` committed or read by a recipe or agent; `check-connections` printing error text, tokens or URLs; an agent running a human-only recipe.
- `cd web && ...` in recipes; hand-edited `schema.d.ts`; an `app/`, `Dockerfile` or `deploy/` creeping back; a bind-address setting or `0.0.0.0` anywhere; `tower-http` `cors` feature; a `just` recipe not in the fragment; `verified_on` bumped without a source.

- [ ] `cargo clippy --workspace --all-targets -- -D warnings` clean; `rust-toolchain.toml`, `rust-version` and CI agree.
- [ ] `pnpm -C web typecheck`, `lint`, `test:ci`, `build` succeed from the repo root; `just openapi` leaves `schema.d.ts` unchanged.
- [ ] Every `config/*.toml` has `schema_version`, `verified_on`, `source`, passes `validate()`, has a fixture twin.
- [ ] `just db-check` prints only `OK <check>` / `FAILED <check> <category>`.
- [ ] Unit tests added or updated for every changed type, config key and calendar rule; no market facts in source; no secrets anywhere.
