## Standards and obligations

WCAG 2.2 level AA is the target. It is the current W3C standard, and the major accessibility laws reference WCAG at level AA. Building to it once covers most markets. WCAG 3.0 is still being developed and isn't a target yet.

| Market | Requirement (summary) | Applies to |
| --- | --- | --- |
| European Union | European Accessibility Act, enforced since 28 June 2025, via the harmonised standard EN 301 549 (which maps to WCAG AA) | Many consumer products and services, including e-commerce, banking and e-books |
| United States | ADA (courts commonly use WCAG 2.1 AA as the benchmark); Section 508 for federal work; a DOJ rule requiring WCAG 2.1 AA for state and local government sites | Businesses open to the public; government and government contractors |
| Elsewhere | Similar laws in the UK, Canada, Australia, India and others, mostly referencing WCAG AA | Varies |

This is a summary, not legal advice. Confirm your obligations with legal counsel, and publish an accessibility statement saying what you meet and how users can report problems.

**What WCAG 2.2 added over 2.1** (often missed in older checklists):

- **Focus not obscured:** a focused element must not be hidden behind sticky headers, cookie banners or chat widgets.
- **Target size (minimum):** pointer targets at least 24×24 CSS px, or spaced so a 24 px circle around each doesn't overlap another.
- **Dragging movements:** anything done by dragging (reordering, sliders) has a single-pointer alternative, such as buttons or a menu.
- **Consistent help:** help links or contact options appear in the same place on every page.
- **Redundant entry:** don't make users re-type information they already entered in the same process; pre-fill it or offer to select it.
- **Accessible authentication:** no cognitive tests (remembering or transcribing codes) without an alternative. Allow paste and password managers, and offer passkeys or magic links.

## Accessible patterns

Most accessibility bugs come from rebuilding standard controls with `div`s. Use the native element when one exists. For complex widgets (combobox, date picker, data grid), use a proven headless library such as React Aria Components instead of hand-rolling keyboard and screen-reader behaviour, and style it with the design-system tokens.

| Need | Build with | Must have |
| --- | --- | --- |
| An action | `<button type="button">` | A visible label, or `aria-label` for icon-only buttons (icon `aria-hidden`) |
| Navigation | `<a href>` with a real URL | Never a button that navigates; opens in a new tab only when the user chooses |
| Modal | Native `<dialog>` via `showModal()` (`fe-design-system`) | Title linked with `aria-labelledby`; focus returns to the trigger |
| Show/hide a section | `<details>`/`<summary>`, or a button with `aria-expanded` and `aria-controls` | State announced; content follows the trigger in reading order |
| Tabs | The pattern below | One tab stop for the tab list; arrow keys move between tabs |
| Autocomplete / combobox | Headless library (React Aria Components) | `aria-expanded`, active option announced, Escape closes, typing never blocked |
| Tooltip | `popover` + anchor positioning (with fallback) | Shows on focus as well as hover, dismissible with Escape, never the only place essential info lives |
| Toast / status message | The announcer below | Errors don't auto-dismiss; pause on hover or focus |
| Data table | `<table>`, `<caption>`, `<th scope>` | Sortable headers are buttons with `aria-sort` on the `<th>` |
| Drag to reorder | Drag **plus** move-up/move-down buttons | A single-pointer alternative (WCAG 2.2) |

**Announce changes without a page load** — `src/shared/ui/announcer.tsx`. Live regions must already be in the page before their content changes, so the provider renders them once at startup:

```tsx
import { createContext, useContext, useState, type ReactNode } from 'react';

type Politeness = 'polite' | 'assertive';
const AnnounceContext = createContext<(message: string, politeness?: Politeness) => void>(() => undefined);

export function AnnouncerProvider({ children }: { children: ReactNode }) {
  const [polite, setPolite] = useState('');
  const [assertive, setAssertive] = useState('');

  const announce = (message: string, politeness: Politeness = 'polite') => {
    const set = politeness === 'polite' ? setPolite : setAssertive;
    set(''); // clear first, so repeating the same message is announced again
    requestAnimationFrame(() => set(message));
  };

  return (
    <AnnounceContext value={announce}>
      {children}
      <div className="visually-hidden" role="status" aria-live="polite">{polite}</div>
      <div className="visually-hidden" role="alert" aria-live="assertive">{assertive}</div>
    </AnnounceContext>
  );
}

export const useAnnounce = () => useContext(AnnounceContext);
```

Use `polite` for confirmations and results ("Order cancelled", "12 results") and `assertive` only for errors that need immediate attention. Example: `onSuccess: () => announce('Order cancelled')` in a mutation.

**Tabs with correct keyboard support** — `src/shared/ui/tabs.tsx`:

```tsx
import { useId, useRef, useState, type KeyboardEvent, type ReactNode } from 'react';

interface TabItem {
  id: string;
  label: string;
  panel: ReactNode;
}

export function Tabs({ label, tabs }: { label: string; tabs: readonly TabItem[] }) {
  const [active, setActive] = useState(0);
  const tabRefs = useRef<(HTMLButtonElement | null)[]>([]);
  const baseId = useId();

  function nextIndex(key: string): number | undefined {
    const last = tabs.length - 1;
    switch (key) {
      case 'ArrowRight': return active === last ? 0 : active + 1;
      case 'ArrowLeft': return active === 0 ? last : active - 1;
      case 'Home': return 0;
      case 'End': return last;
      default: return undefined;
    }
  }

  function onKeyDown(event: KeyboardEvent<HTMLDivElement>) {
    const next = nextIndex(event.key);
    if (next === undefined) return;
    event.preventDefault();
    setActive(next);
    tabRefs.current[next]?.focus(); // roving focus: only the active tab is in the Tab order
  }

  return (
    <div>
      <div role="tablist" aria-label={label} onKeyDown={onKeyDown}>
        {tabs.map((tab, i) => (
          <button
            key={tab.id}
            ref={(el) => {
              tabRefs.current[i] = el;
            }}
            type="button"
            role="tab"
            id={`${baseId}-tab-${tab.id}`}
            aria-selected={i === active}
            aria-controls={`${baseId}-panel-${tab.id}`}
            tabIndex={i === active ? 0 : -1}
            onClick={() => setActive(i)}
          >
            {tab.label}
          </button>
        ))}
      </div>
      {tabs.map((tab, i) => (
        <div
          key={tab.id}
          role="tabpanel"
          id={`${baseId}-panel-${tab.id}`}
          aria-labelledby={`${baseId}-tab-${tab.id}`}
          hidden={i !== active}
          tabIndex={0}
        >
          {tab.panel}
        </div>
      ))}
    </div>
  );
}
```

If the selected tab should survive a refresh or be shareable, keep it in a URL search param (`fe-app-architecture`) and pass `active` in as a prop.

**Focus management moments**

| Moment | Move focus to |
| --- | --- |
| Route change | The page's `<main>` or `<h1>` (`fe-app-architecture`'s root layout does this) |
| Dialog opens / closes | First focusable element or the safe action / back to the trigger (native `<dialog>` does both) |
| Form submitted with errors | An error summary at the top listing each error as a link to its field |
| Deleting the focused item in a list | The next item, or the list heading if it was the last one |
| Content loaded in place ("Load more") | Stay put; announce "20 more orders loaded" |

## Visual accessibility

Most visual requirements are met once, in the design tokens and base CSS (`fe-design-system`), and then inherited by every component. This section lists the bars to hit and the few CSS patterns that keep them true.

| Requirement (WCAG 2.2 AA) | Bar | Where it's handled |
| --- | --- | --- |
| Text contrast | 4.5:1 for body text; 3:1 for large text (24 px, or 18.7 px bold) | Semantic colour tokens; check every text/background pair in both themes |
| Non-text contrast | 3:1 for borders of inputs, focus indicators, icons that carry meaning | Tokens `--color-border`, `--color-focus` |
| Colour alone | Never the only signal (errors, status, links in text) | Status badges carry text; links are underlined; errors have an icon and message |
| Resize and reflow | Usable at 200% text size and at 320 CSS px wide (400% zoom) without horizontal scrolling | `rem` units, container queries, no fixed heights on text containers |
| Text spacing | Survives users increasing line, letter and word spacing | No fixed-height boxes around text; let content grow |
| Focus visible and not obscured | Every focusable element shows a clear indicator, never hidden under sticky headers | Global `:focus-visible` style; `scroll-padding-top` equal to the sticky header height |
| Target size | At least 24×24 CSS px | `--control-height-*` tokens (32–48 px) |
| Motion | Nothing flashes more than 3 times per second; auto-playing motion longer than 5 s can be paused | Reduced-motion rules below; no auto-playing carousels without a pause button |

**Respect user preferences in CSS**

```css
/* Sticky headers must not cover the focused element (WCAG 2.2 "focus not obscured") */
html {
  scroll-padding-block-start: calc(var(--header-height) + var(--space-4));
}

/* Reduced motion: remove decorative movement, keep meaningful feedback (instant instead of animated) */
@media (prefers-reduced-motion: reduce) {
  .slideIn { animation: none; }
  .parallax { transform: none; }
}

/* Forced colours (Windows high contrast): backgrounds and shadows are removed, so keep visible boundaries */
@media (forced-colors: active) {
  .button { border: 1px solid ButtonText; }
  .card { border: 1px solid CanvasText; }
}
```

**Rules that prevent common visual failures**

- **Draw focus rings with `outline`, never only `box-shadow`.** Forced-colours mode removes shadows, and keyboard users lose their place.
- **Never `outline: none` without a replacement** that meets 3:1 contrast against the background.
- **Placeholders are not labels.** They disappear on typing and usually fail contrast.
- **Disabled controls are exempt from contrast rules, but explain why something is disabled** next to it, so the user isn't stuck.
- **Test both themes.** A colour pair that passes in light mode often fails in dark mode.

## Testing accessibility

Automated tools reliably catch the mechanical problems: missing labels, bad contrast, invalid ARIA, duplicate ids. They can't judge whether a focus order makes sense, whether an announcement is understandable, or whether a flow is usable without seeing the screen. So automate every check that can be automated, and run a short manual script on every new flow.

**Automated layers** (most already set up in earlier docs)

| Layer | Catches | Where |
| --- | --- | --- |
| `eslint-plugin-jsx-a11y` | Missing `alt`, click handlers on non-interactive elements, invalid ARIA | Every commit (`fe-repo-foundation`) |
| Queries by role and label in tests | Elements a screen reader can't name or identify | Every component test (`fe-testing`) |
| Storybook a11y addon (`a11y: { test: 'error' }`) | axe violations in every component state and theme | Every PR (`fe-design-system`) |
| Playwright + axe on key pages and states | Page-level issues: landmarks, headings, contrast in context | Every PR (smoke) and merge queue |
| Lighthouse accessibility score ≥ 95 | Regression signal on public pages | PR preview (`fe-performance`) |

**`e2e/a11y.spec.ts`** — scan every key page, and the states that only appear after interaction:

```ts
import { test, expect } from './fixtures';
import AxeBuilder from '@axe-core/playwright';

const WCAG_TAGS = ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'];
const pages = ['/', '/orders', '/orders/new', '/settings'];

for (const path of pages) {
  test(`${path} has no WCAG A/AA violations`, async ({ page }) => {
    await page.goto(path);
    const { violations } = await new AxeBuilder({ page }).withTags(WCAG_TAGS).analyze();
    expect(violations.map((v) => `${v.id} (${v.nodes.length})`)).toEqual([]); // readable failure list
  });
}

test('cancel dialog is accessible when open', async ({ page, seedOrder }) => {
  const order = await seedOrder();
  await page.goto(`/orders/${order.id}`);
  await page.getByRole('button', { name: 'Cancel order' }).click();
  await expect(page.getByRole('dialog')).toBeVisible();
  const { violations } = await new AxeBuilder({ page }).include('dialog').withTags(WCAG_TAGS).analyze();
  expect(violations).toEqual([]);
});
```

**Manual test script** — about 15 minutes per new flow, done by the author before review and spot-checked by the reviewer:

| Check | How | Pass when |
| --- | --- | --- |
| Keyboard only | Unplug the mouse; use Tab, Shift+Tab, Enter, Space, Escape, arrow keys | Every action is reachable, focus is always visible, the order is logical, nothing traps focus |
| Screen reader smoke test | macOS VoiceOver (Cmd+F5; VO = Ctrl+Option; VO+U opens the rotor) or Windows NVDA (H jumps between headings, D between landmarks, NVDA+F7 lists elements) | The page title, headings and landmarks make sense; every control has a meaningful name; changes and errors are announced |
| Zoom | Browser zoom to 200%, then 400% (320 px wide) | No content lost or overlapping; no horizontal scrolling except data tables |
| Forced colours | Windows contrast themes, or Chrome DevTools → Rendering → Emulate forced-colors | Controls, borders and focus rings stay visible |
| Reduced motion | OS setting, or DevTools → Rendering → Emulate prefers-reduced-motion | No large movement remains; nothing depends on an animation finishing |
| Mobile screen reader (release-level) | iOS VoiceOver, Android TalkBack | Touch exploration and swipe navigation work through the main journey |

**Beyond the team** — schedule an expert accessibility audit at least yearly and before major launches. Include people with disabilities in usability testing; they find problems no checklist anticipates.
