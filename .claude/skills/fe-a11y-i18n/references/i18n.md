## Translation pipeline

*Diagram: translation pipeline · from message to per-locale bundle*

Engineers only ever touch the first box. Extraction, translation, validation and code-splitting are automated, so adding a language is a configuration change, and a translator's typo can't break the build. Pseudo-locales let you test long text and right-to-left before real translations exist.

## i18n setup

Use FormatJS (`react-intl`). It implements the ICU MessageFormat standard (plurals, selects, rich text), delegates formatting to the browser's built-in `Intl` APIs, and can precompile messages at build time, so no parser ships to users. Earlier docs hard-code English strings for readability; in a real app, every user-facing string goes through a message like those below.

```bash
pnpm add react-intl
pnpm add -D @formatjs/cli eslint-plugin-formatjs
```

**Writing messages** — an explicit, readable id, the English default, and a description for translators:

```tsx
import { defineMessages, FormattedMessage, useIntl } from 'react-intl';

const messages = defineMessages({
  count: {
    id: 'orders.list.count',
    defaultMessage: '{count, plural, =0 {No orders} one {# order} other {# orders}}',
    description: 'Total number of orders shown above the orders table',
  },
  empty: {
    id: 'orders.list.empty',
    defaultMessage: 'No orders match these filters.',
    description: 'Empty state when filters exclude every order',
  },
});

export function OrdersSummary({ count }: { count: number }) {
  const intl = useIntl();
  return <p>{intl.formatMessage(messages.count, { count })}</p>;
}

// Rich text: the link stays inside one translatable sentence
<FormattedMessage
  id="checkout.terms"
  defaultMessage="By paying you accept our <link>terms of service</link>."
  description="Legal note under the Pay button"
  values={{ link: (chunks) => <a href="/terms">{chunks}</a> }}
/>;
```

**Message rules, enforced by `eslint-plugin-formatjs`** — enable `enforce-description`, `enforce-default-message`, `enforce-placeholders` and `no-literal-string-in-jsx` in the shared ESLint config:

| Wrong | Right | Why |
| --- | --- | --- |
| `` `${count} items` `` | `{count, plural, one {# item} other {# items}}` | Polish has 3 plural forms, Arabic 6 |
| `'Hello ' + name + ', welcome back'` | `'Hello {name}, welcome back'` | Word order differs; translators must see the whole sentence |
| Reusing `common.open` for both "Open (verb)" and "Open (status)" | Separate messages with descriptions | Many languages translate the two differently |
| `<b>Note:</b> {text}` as two messages | One message with `<b>` rich-text tags | Translators may need to move the emphasis |

**Scripts** — extract English source messages, then compile all locales to precompiled ASTs:

```json
{
  "i18n:extract": "formatjs extract \"src/**/*.{ts,tsx}\" --ignore \"**/*.d.ts\" --format simple --out-file lang/en.json",
  "i18n:compile": "formatjs compile-folder --ast --format simple lang src/i18n/compiled"
}
```

**`src/app/i18n.ts`** — locale negotiation, lazy loading and document direction:

```ts
import type { MessageFormatElement } from 'react-intl';

export const SUPPORTED_LOCALES = ['en', 'es', 'de', 'ja', 'ar'] as const;
export type Locale = (typeof SUPPORTED_LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'en';
const RTL_LOCALES = new Set<Locale>(['ar']);

/** First supported match from the user's saved choice, then browser preferences. */
export function negotiateLocale(preferred: readonly string[]): Locale {
  for (const tag of preferred) {
    const base = tag.toLowerCase().split('-')[0];
    const match = SUPPORTED_LOCALES.find((locale) => locale === base);
    if (match) return match;
  }
  return DEFAULT_LOCALE;
}

/** Each locale becomes its own chunk: users download only their language. */
export async function loadMessages(locale: Locale): Promise<Record<string, MessageFormatElement[]>> {
  const module = (await import(`../i18n/compiled/${locale}.json`)) as { default: Record<string, MessageFormatElement[]> };
  return module.default;
}

export function applyDocumentLocale(locale: Locale): void {
  document.documentElement.lang = locale; // screen readers pick the right voice and pronunciation
  document.documentElement.dir = RTL_LOCALES.has(locale) ? 'rtl' : 'ltr';
}
```

**Startup** (in `main.tsx`, before rendering):

```tsx
const savedLocale = localStorage.getItem('locale'); // mirrored from the user's profile setting
const locale = negotiateLocale([...(savedLocale ? [savedLocale] : []), ...navigator.languages]);
const messages = await loadMessages(locale);
applyDocumentLocale(locale);

// wrap the app:
<IntlProvider locale={locale} defaultLocale={DEFAULT_LOCALE} messages={messages} timeZone={userTimeZone} onError={reportError}>
  <AppProviders queryClient={queryClient} router={router} />
</IntlProvider>;
```

When a user changes language, save it to their profile and reload the page; a reload is simpler and safer than swapping every message and cached formatter at runtime.

**Formatting** — always through `intl` (which wraps `Intl` with the active locale and time zone), never with hand-written formats:

| Value | Call | `en-US` / `de-DE` output |
| --- | --- | --- |
| Date | `intl.formatDate(order.createdAt, { dateStyle: 'medium' })` | Oct 1, 2026 / 01.10.2026 |
| Date and time | `intl.formatDate(ts, { dateStyle: 'short', timeStyle: 'short' })` | 10/1/26, 3:30 PM / 01.10.26, 15:30 |
| Money | `intl.formatNumber(cents / 100, { style: 'currency', currency })` | $49.99 / 49,99 $ |
| Number | `intl.formatNumber(12345.6)` | 12,345.6 / 12.345,6 |
| Relative time | `intl.formatRelativeTime(-3, 'day', { numeric: 'auto' })` | 3 days ago / vor 3 Tagen |
| List | `intl.formatList(['Ana', 'Ben', 'Chen'], { type: 'conjunction' })` | Ana, Ben, and Chen / Ana, Ben und Chen |

Store timestamps in UTC (ISO 8601 strings from the API) and pass the user's time zone, from their profile or `Intl.DateTimeFormat().resolvedOptions().timeZone`, to `IntlProvider`. A Monday-9am deadline then displays correctly in every city.

## Right-to-left layouts and translation workflow

**Right-to-left (Arabic, Hebrew, Persian, Urdu)** — with `dir="rtl"` on `<html>` and logical CSS properties throughout (`fe-design-system`), most of the layout mirrors itself. The remaining work is a handful of details:

| Item | Rule |
| --- | --- |
| Spacing and positioning | Logical properties only: `margin-inline-start`, `padding-inline`, `inset-inline-end`, `text-align: start`. Stylelint can ban `left`/`right` variants |
| Directional icons (back, next, chevrons, "reply") | Mirror them in RTL; leave non-directional icons alone (checkmarks, play, logos, clocks) |
| User-generated text inside a sentence | Wrap it in `<bdi>`, so an English name in an Arabic sentence (or vice versa) doesn't scramble the punctuation |
| Numbers, phone numbers, codes | Keep them left-to-right inside RTL text with `<bdi>` or `dir="ltr"` on that element |
| Fonts | Make sure the font stack covers each script; system fonts do |

```css
/* Mirror only icons that point in a reading direction */
:dir(rtl) .icon[data-directional] {
  transform: scaleX(-1);
}
```

**Leave room for longer text.** German and Finnish strings often run 30–40% longer than English. Avoid fixed widths on buttons and labels, allow wrapping, and check layouts with pseudo-localization.

**Pseudo-localization** — generate fake locales that look like translations, so problems show up before any translator is involved:

```json
{
  "i18n:pseudo": "formatjs compile lang/en.json --ast --pseudo-locale en-XA --out-file src/i18n/compiled/en-XA.json && formatjs compile lang/en.json --ast --pseudo-locale en-XB --out-file src/i18n/compiled/en-XB.json"
}
```

`en-XA` adds accents and brackets (`[Ńöö öŕðéŕš]`), so any unbracketed text on screen is a hard-coded string. `en-XB` forces right-to-left, so you can test mirroring without reading Arabic. Enable both locales in development and staging only.

**Translation workflow**

1. **Engineers write messages** with descriptions and English defaults; nothing else.
2. **CI checks extraction:** `pnpm i18n:extract && git diff --exit-code lang/en.json` fails a PR whose new strings weren't extracted.
3. **The translation management system** (Crowdin, Lokalise or Phrase, through its GitHub integration) picks up `lang/en.json` from `main`. Translators work with the descriptions and screenshots attached to each key.
4. **The system opens a PR** with updated `lang/<locale>.json` files. CI compiles them, and the compile step rejects broken ICU syntax, so a translator's typo can't crash the app.
5. **Missing translations fall back to English** at runtime and are reported as coverage per locale. Features can ship before every translation is in, but a locale isn't advertised until it's complete.

**Rules for keys**

- Ids are stable and meaningful (`orders.list.empty`). Renaming one throws away its translations, so change the default message, not the id, when wording changes slightly.
- Change the id when the **meaning** changes, so stale translations aren't shown for a different sentence.
- Delete unused messages: extraction drops them from `en.json`, and the translation system archives them.
